## Account mapping is more than attaching a credential

The practice reservation is in telegram_restricted_learners. A local_bot_id of null identifies the one private learner account for a Telegram ID across bots. If an independent account association already exists without a grant for this bot, enrollment creates an isolated owner with that bot ID instead. Only the first kind is a candidate for same-account recovery. Do not promote a bot-local owner into another independently earning account.

Enrollment inserts a users row without a complete account document or provider credential. It reserves the first persona through existing database behavior and creates a separate community Study persona with a pending wallet assignment. Ordinary identity registration generates a new account and first-persona preparation. Solid automatically calls that registration path after a session-exchange 401. A connection entry must intercept before that generic bootstrap; otherwise it can create a second Pirate account.

Ordinary session exchange also loads the full IdentityAccountDocument and requires product readiness: an active first persona with an active EVM wallet assignment. A practice reservation is not already a complete website account. Even adding its provider credential would not make the current exchange succeed. The recovery contract must explicitly specify in-place profile/handle and first-persona preparation, or a separate browser session limited to practice-history management. It must preserve the ordinary full-session wallet gate. Do not turn a failed exchange into an automatic new-account registration or weaken global readiness to make the spike pass.

There is a separate database restriction after readiness: migration 0246's require_restricted_learner_practice_only trigger refuses every non-practice Study session for an account still present in telegram_restricted_learners. A recovered credential, completed profile and active first wallet do not lift it. Future ordinary-Study admission therefore needs an explicit reviewed recovery transition, or the initial recovery must remain limited to practice-history management. Preserve the reservation and account/persona/session identifiers; do not delete the reservation to bypass the trigger. Historic lessons remain permanently practice-only and never acquire reward eligibility. This is an existing implementation boundary, not a change made by this research.

The current Solid OAuth controller navigates the whole window after generateURL while the SDK storage is memory-only; its callback constructs a fresh exchange. The installed OAuth loginWithCode reads the original verifier and state from that storage. The probe must demonstrate actual redirect continuity instead of copying that controller blindly. A reviewed popup preserving the initiating SDK instance, or server-owned transient continuation, needs exact Origin/window/state checks and safe refusal if the browser cannot support it. Do not add localStorage or transfer secrets through chat to preserve continuity.

The existing proof adapter verifies a Privy access token's application, issuer, subject and lifetime, but returns no Telegram ID. Its provider-owned user lookup currently selects linked wallets only. A recovery verifier must obtain and validate the numeric Telegram identity from the correctly verified provider result, using a fresh app/subject-bound signed identity result or the existing managed server-side provider lookup. A browser-supplied Telegram ID, unverified SDK user object, username or decoded-but-unverified JWT is insufficient. Bound responses, identity freshness, replay and account conflicts must fail closed. Discard unrelated provider profile data.
